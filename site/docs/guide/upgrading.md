# Upgrading & Releases

## Tested With

| Area | Tested or declared with | Notes |
| --- | --- | --- |
| Runtime | PHP 8.1+ | The project requirement is `php: >=8.1.0`; test the PHP version used by production. |
| Dependencies | Composer | Load `vendor/autoload.php` in scripts and example front controllers. |
| Documentation | VitePress 1.6.x | The site uses the VitePress 1 configuration format; no dependency upgrade is required for this guide. |
| Production | OPcache (optional) | Helpful when loading generated `*.pure.php` and `*.plain.php` files. |

These are compatibility and documentation targets, not a promise that every
future PHP or extension combination has been tested.

## Upgrade checklist

For a tagged release, update the Composer constraint in your application and run:

```bash
composer update yonld/purephp
composer test
```

When following the default branch, pin the tested commit in your application
instead of inventing a release number. Before deploying that commit:

1. Review the [CHANGELOG](https://github.com/YonLD/purephp/blob/main/CHANGELOG.md)
   and the [migration notes](#migration-notes) below.
2. Run `composer quality` in the library checkout.
3. Run `vendor/bin/pure check <paths>` for component and shape units.
4. Rebuild strict and plain artifacts:

   ```bash
   vendor/bin/pure compile <paths>
   vendor/bin/pure compile --plain <paths>
   vendor/bin/pure compile --check --plain <paths>
   ```

5. Exercise the [examples](/guide/examples), including a strict route, a plain
   route, the static `/cover` route, and the XML CLI writer.
6. If the application uses `Compile::cachePath()`, remove only the cache files
   owned by PurePHP when the release requires regeneration. `Compile::clearCache()`
   is the explicit API for that operation.
7. Verify the rendered output and document headers, then deploy the source and
   generated artifacts together.

Do not hand-edit `*.pure.php` or `*.plain.php`. They contain a cache-version or
fingerprint contract and must be regenerated by the matching compiler.

## Migration notes

The migration-sensitive pieces are:

### Component units derive their name from the call function

The recommended registration form is now:

```php
register(Card(...), factory: static fn () => div(...));
```

The call function returns `component(__FUNCTION__)`, or
`component(__FUNCTION__, ...$children)` when its template reads the `children`
slot. This keeps the component name and its unit file in one place. Update older
examples that passed a duplicated name literal, and use `override: true` only
when an intentional replacement is required.

### Template builders are explicit

A `#[Template]` function marks a shape builder beside a unit. `pure compile --list`
reports it as `(template)`, and `pure check` validates its declared return type.
Do not confuse this marker with a separate page type.

### Artifacts carry compatibility guards

Generated strict artifacts contain a cache-version guard. If a deployed artifact
was written by another cache generation, run `pure compile`; do not bypass the
exception or copy the artifact between incompatible deployments. Plain views are
generated views and should be checked with `--check --plain`.

### Contract attributes are tooling declarations

`#[Prop]`, `#[Trusted]`, and `#[Binds]` are read by `pure check`; `#[Prop]` and
`#[Trusted]` also feed the development guard. They do not sanitize values or
change rendering. Review
their contracts when upgrading a component, especially when a raw slot now
receives markup. See [Component API](/api/component).

## Deploying a release

A release should be prepared from a reviewed commit with:

- a dated entry in `CHANGELOG.md` under a real SemVer heading;
- a Git tag matching that heading and the Composer package version;
- passing syntax, style, PHPStan, and PHPUnit checks;
- fresh `*.pure.php` and, when used, `*.plain.php` artifacts;
- a smoke test of the examples and a cache rebuild when the cache version changes.

The site does not publish a versioned `/vX/` copy until such a tag exists.

## Rollback

If a deployment fails, roll back the application source and its generated
artifacts as one unit. Then clear the PurePHP renderer cache, rerun
`vendor/bin/pure compile --check`, and check the first failing route. Keeping a
known-good artifact beside its source is safer than restoring only one of the two.
